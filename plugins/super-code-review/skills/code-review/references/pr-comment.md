# レビュー結果のPRコメント投稿

`code-review` / `iterative-review` / `pr-review` / `pr-respond` が PR にコメントを投稿するときのルール。

ユーザーから「レビュー結果をPRにコメントして」等の明示的な依頼があった場合のみ、`gh pr comment` でレビュー結果を投稿してください（`pr-review` はスキルの呼び出しを依頼とみなす）。依頼がない限り自動投稿はしないこと。`gh pr comment` は allowed-tools に入れていない（`pr-review` を除く）ため、実行時にユーザーの確認が出る。投稿時は以下のルールを厳守する：

## 1. `#` の文字を使わない

GitHub 上では `#` + 数字が**他の PR / issue への自動リンク**になるため、コメント本文では `#` を一切使わない：
- 指摘番号は `#3` ではなく **`F-3`** と表記する
- Markdown 見出し（`#` / `##` 等）も使わず、`**太字**`・水平線（`---`）・`<details>` で構造化する

## 2. 基本は通常コメント（インラインコメントは使わない）

- **PR 全体への通常コメント**として投稿する（手順は下記 4）
- 特定行へのインラインコメント（review comment）は、ユーザーが明示的に指定した場合のみ使用する

## 3. レビュー結果をそのまま貼らず、読みやすく再整形する

`code-review/SKILL.md` の「出力形式」はターミナル閲覧用であり、PRコメントには**レビューコメントとして読みやすい形に再整形**して投稿する。PR の作成者は AI を使わずに直すこともあるため、ターミナル出力では1行に縮めた指摘にも、コメントでは直し方の詳細を付ける：

- **冒頭 2〜4 行で要約**: Verdict・変更概要・推奨アクションを最初に書き、受領者が3秒で判断できる形にする（仕様・挙動ベースの説明を優先し、内部用語の羅列を避ける）
- **確認してほしいこと（人の判断が必要な指摘）は本文に出す**: ターミナル出力と同じく、どういうことか・なぜ判断が必要か・選択肢を書く
- **修正をおすすめする点は一覧 + トグル**: `F-1` 形式の番号 + `File:Line` + 1行サマリを本文に並べ、何が問題か / 影響 / 修正方針は `<details><summary>詳細</summary>` に畳む
- **別タスク候補は1行ずつ**、まとめて `<details>` に畳んでよい
- **出さないもの**: ターミナル出力で出さないもの（除外した指摘・エージェントごとの内訳）はコメントにも出さない
- **ターミナル向け装飾を持ち込まない**: `─────` のような罫線・絵文字テンプレートは使わず、GitHub Markdown（テーブル・`<details>`・太字・バッククォート）で表現する
- **コードシンボルのバッククォートは維持**する

## 4. 投稿手順

1. 整形したコメント本文を、標準入力から `gh` に渡す（ファイルを書き出さず、シェルのエスケープ事故も防ぐため。引用符付きのヒアドキュメントを使う）

```bash
gh pr comment <PR番号> --body-file - <<'SCR_EOF'
<本文>
SCR_EOF
```

2. 本文に `SCR_EOF` だけの行が含まれないことを確かめる（含まれる場合は区切り文字を変える）
3. 投稿前に、本文に秘密情報らしい文字列（`KEY=`、`-----BEGIN`、`ghp_`、`sk-` 等）が含まれていないか確かめる。含まれていれば投稿せず、ユーザーに確認する（`review-rules.md` の「秘密情報の書き方」）
4. 投稿後、コメントの URL をユーザーに報告する
